# 文件管理宪法 · File Management Constitution

> **一句话原则**：先按"谁管的"分区，再按"怎么找"分类。永远不在同一个区里混用两种逻辑。

**版本**：v2.3（通用版·已部署）
**创建日期**：2026-08-06
**适用范围**：整个电脑、任何职业（程序员/作家/财务/会计/架构师/研究员...）
**部署位置**：G:\（试验场）

---

## 〇、为什么需要这套体系

### 问题本质

大多数人整理文件的方式是**按内容分类**（这是工作？还是个人？是代码？还是文档？）。但这种方式有三个致命缺陷：

**缺陷 1：分类逻辑 ≠ 检索逻辑**
- 你按"内容"归档（"这是经济学笔记"）
- 但你找文件时想的是场景（"我上周做那个项目时的数据"）
- 每次归档都要做一次"心智翻译"→ 累积摩擦 → 放弃整理

**缺陷 2：无法容纳"非主动创建"的文件**
- 你精心设计了 01~08 的编号分类
- 但 CUDA 缓存、HuggingFace 缓存、微信文件、下载文件夹、Ollama 模型……
- 这些是**应用/环境自己长出来的**，你的分类法没有给它们预留位置
- 于是它们溢出到根目录 → 编号体系从内部瓦解

**缺陷 3：临时文件没有生命周期**
- "我先建个临时文件夹试试" → `temp_proj/`、`TestProj/`、`新建文件夹/`
- 试完不删 → 永久驻留 → 和正式项目混在一起
- 一个月后：哪些是临时的？哪些是正式的？没人知道了

### 解决思路

回到第一性原理：**一台电脑上的文件，按"谁把它放在这里的"分为三类。**

| 类型 | 谁放的 | 管理逻辑 |
|---|---|---|
| 🎯 **我管的** | 你主动创建/下载/整理的 | 按关系分区 + 区内自治分类 |
| ⚙️ **机器管的** | 应用/环境/系统自动生成的 | 隔离到环境区，不碰 |
| 🔄 **流动中的** | 暂时的、还没决定归属的 | 统一入口 + 定期清理 |

**这三类文件用三套完全不同的逻辑管理，永远不混在同一个目录里。**

## 一、顶层结构：3+1 模型

```
G:\  ← 试验场（276GB 空闲，已部署）
│
├── 🎯 MINE/          ← 我管的——你的主动产出和资料
│   ├── 10-Work/         本职工作（按项目）
│   ├── 20-Projects/     个人/副业项目（按项目）
│   ├── 30-Knowledge/    知识库（按主题）
│   ├── 40-Personal/     个人事务（按事务类型）
│   ├── 50-Creative/     创作产出（按作品）
│   ├── 60-Learning/     学习材料（按来源/主题）
│   ├── 70-Archive/      归档（按年份+来源）
│   └── 90-Misc/         杂项
│
├── ⚙️ SYSTEM/        ← 机器管的——应用、环境、依赖（隔离区）
│   ├── _AppData/        应用数据（微信、网盘等）
│   ├── _DevEnv/         开发环境（SDK、CUDA、依赖库）
│   ├── _Cache/          缓存（HuggingFace、Ollama等）
│   ├── _Software/       绿色软件
│   └── _VM/             虚拟机/容器
│
├── 🔄 INBOX/         ← 流动中的——缓冲区，定期清理
│   ├── _Downloads/      下载（替代系统下载文件夹）
│   ├── _Scratch/        临时草稿、截图
│   └── _ToDecide/       待决策（7天上限）
│
├── _INDEX.md         ← 宪法（本文件）
│
├── Cognition/        ← 已有知识库（保持独立运行）
├── AI-Money/         ← 已有项目（保持独立运行）
└── OpenTools/        ← 已有工具（保持独立运行）
```

> **每个目录下都有 `_README.md` 微型宪法**，说明该目录的用途和规则。
> **已有的 Cognition/AI-Money/OpenTools 不受影响**，保持独立运行。

> **关于盘符**：每个数据盘可以用这套结构。系统盘（C:）不建议用，C 盘让操作系统和软件自己管。
>
> **关于命名**：`MINE`、`SYSTEM`、`INBOX` 是概念名。实际可以用任何你习惯的语言（我的/系统/收件箱），但**三个区的功能边界不能模糊**。

## 二、三个区的详细规则

### 🎯 MINE/ —— 我管的文件

**这里放什么**：你主动创建、下载、整理的所有文件。项目、文档、知识、数据、设计稿、财务表……凡是"你决定放在这里的"，都进 MINE。

**这里不放什么**：
- ❌ 应用自动生成的缓存/配置（→ SYSTEM）
- ❌ 还没决定怎么处理的文件（→ INBOX）
- ❌ 开发环境/SDK/依赖库（→ SYSTEM）

#### MINE 内部分类：按"关系类型"分区

> **关键洞察**：不要在 MINE 内部按"内容"分类（文档/图片/视频/代码），要按**"这个文件和我处于什么关系"**分类。

```
MINE/
├── 10-Work/          ← 本职工作
├── 20-Projects/      ← 个人/副业项目
├── 30-Knowledge/     ← 知识库（长期积累）
├── 40-Personal/      ← 个人事务（财务/健康/证件/生活）
├── 50-Creative/      ← 创作产出（写作/设计/视频/音乐）
├── 60-Learning/      ← 学习材料（课程/教程/书籍）
├── 70-Archive/       ← 归档（完成/过期/不确定要不要留）
└── 90-Misc/          ← 杂项（不属于以上的东西）
```

**为什么用 10/20/30 而不是 1/2/3**：间隔 10 是为了留插入空间。未来要加一个区，插 `15-XXX` 即可，不影响已有。

#### 每个区的自治规则

**每个区用什么分类维度，由该区的文件性质决定——不强制统一：**

| 区 | 文件性质 | 推荐分类维度 | 示例 |
|---|---|---|---|
| `10-Work` | 高熵，不断产生 | **按项目/任务** | `10-Work/分割分级项目/` |
| `20-Projects` | 高熵 | **按项目** | `20-Projects/MoneyPrinterTurbo/` |
| `30-Knowledge` | 低熵，结构稳定 | **按主题/学科** | `30-Knowledge/01-Mental-Models/` |
| `40-Personal` | 中熵 | **按事务类型** | `40-Personal/财务/`、`40-Personal/保险/` |
| `50-Creative` | 中熵 | **按作品/系列** | `50-Creative/小说/`、`50-Creative/视频/` |
| `60-Learning` | 中熵 | **按来源/主题** | `60-Learning/Coursera-ML/` |
| `70-Archive` | 中熵 | **按年份+来源** | `70-Archive/2026/from-Work/` |
| `90-Misc` | 低熵 | 随意 | 塞进去就行 |

> **职业适配**：
> - **程序员**：`10-Work` 里按项目分代码仓库，`20-Projects` 放个人开源项目
> - **作家**：`50-Creative` 是主战场，按作品系列分
> - **财务/会计**：`40-Personal/财务` 或 `10-Work` 按年度/账期分
> - **架构师**：`30-Knowledge` 放架构模式，`10-Work` 放项目设计文档
> - **研究员**：`60-Learning` 放论文，`10-Work` 或 `20-Projects` 放实验

#### 分区判断流程

```
一个文件要放进 MINE
    │
    ├── 是本职工作产生的？
    │       → 10-Work/[项目名]/
    │
    ├── 是个人/副业项目？
    │       → 20-Projects/[项目名]/
    │
    ├── 是要长期记住的知识？
    │       → 30-Knowledge/[主题]/
    │
    ├── 是个人生活事务？（财务/保险/证件/医疗）
    │       → 40-Personal/[事务类型]/
    │
    ├── 是我的创作产出？
    │       → 50-Creative/[作品名]/
    │
    ├── 是我在学的东西？
    │       → 60-Learning/[课程/主题]/
    │
    ├── 已经完成/过期/不确定要不要留？
    │       → 70-Archive/[年份]/from-[来源]/
    │
    └── 以上都不是？
            → 90-Misc/
```

> **如果 90-Misc 超过 20 个文件**：说明你需要新增一个分区。参考第四节「自我生长机制」。

### ⚙️ SYSTEM/ —— 机器管的文件

**这里放什么**：一切**不是你主动创建的、由应用/环境/系统自动生成或需要的**文件。

**核心原则：你不整理它，你只隔离它。** 让应用在自己的目录里随便长，只要不跑到 MINE 和 INBOX 里就行。

#### SYSTEM 内部结构

```
SYSTEM/
├── _AppData/         ← 应用数据（微信文件、百度网盘下载等）
├── _DevEnv/          ← 开发环境（SDK/依赖库/编译工具）
├── _Cache/           ← 各种缓存（HuggingFace/Ollama/pip/npm...）
├── _Software/        ← 安装的绿色软件（非系统盘的 Program Files）
└── _VM/              ← 虚拟机/Docker/WSL 镜像（如有）
```

#### 如何把"野生目录"迁入 SYSTEM

| 你 E 盘的野生目录 | 迁入位置 |
|---|---|
| `BaiduNetdiskDownload/` | `SYSTEM/_AppData/BaiduNetdisk/` |
| `WeixinFile/` | `SYSTEM/_AppData/WeChat/` |
| `hf_cache/` | `SYSTEM/_Cache/HuggingFace/` |
| `ollama_models/`、`Ollama/` | `SYSTEM/_Cache/Ollama/` |
| `SuperAI_grade_cache/` | `SYSTEM/_Cache/SuperAI/` |
| `cuda111trt8531/`、`cuda128trt1010/` | `SYSTEM/_DevEnv/CUDA-TRT/` |
| `CppDependenceX64/` | `SYSTEM/_DevEnv/` |
| `nvml/` | `SYSTEM/_DevEnv/` |
| `Program Files/` | `SYSTEM/_Software/` |
| `编译工具/` | `SYSTEM/_DevEnv/` |

#### 重要：迁移后要改应用配置

把 `hf_cache/` 移到 `SYSTEM/_Cache/HuggingFace/` 后，需要设置环境变量：
```
HF_HOME=E:\SYSTEM\_Cache\HuggingFace
```

Ollama 模型路径同理：
```
OLLAMA_MODELS=E:\SYSTEM\_Cache\Ollama
```

百度网盘/微信的文件保存路径在应用设置里改。

> **如果你不想改配置**：也可以不移动，只在根目录给它建一个符号链接指向 SYSTEM。但最干净的方式是改应用配置。

---

### 🔄 INBOX/ —— 流动中的文件

**这里放什么**：所有新进来的、还没决定归属的文件。

**核心原则：INBOX 是临时中转站，不是仓库。** 进来的东西必须在限期内出去。

```
INBOX/
├── _Downloads/       ← 替代系统下载文件夹
├── _Scratch/         ← 临时草稿、截图、实验数据
└── _ToDecide/        ← "不知道怎么归类"的文件
```

#### 四条铁律

1. **唯一入口**：所有新文件（下载、截图、别人发的、临时产生的）先进 INBOX
2. **桌面清零**：桌面只放快捷方式，不放实体文件
3. **7 天上限**：`_ToDecide/` 超过 7 天必须决策——归入 MINE / 归档 / 删除
4. **定期清理**：每周一次，花 10 分钟把 INBOX 清空

#### 清理决策树

```
INBOX 里的文件
    │
    ├── 是某个项目/工作的产出？ → MINE/10-Work 或 20-Projects
    ├── 是知识类内容？           → MINE/30-Knowledge
    ├── 是个人事务？             → MINE/40-Personal
    ├── 是创作产出？             → MINE/50-Creative
    ├── 是学习材料？             → MINE/60-Learning
    ├── 用完了，以后可能还翻？   → MINE/70-Archive
    └── 确定不再用？             → 删除
```

## 三、文件生命周期——一个文件会经历什么

> **核心认知：文件的归类不是一次性判决，而是一个生命周期。** 你不需要在文件刚进来时就做"最终判断"，只需要回答"它现在和我的关系是什么"。

### 生命周期四阶段

同一个文件，随着你和它的关系变化，会在不同区域之间迁移：

``````
阶段 1：刚进来（还没决定怎么用）
    INBOX/_ToDecide/
    |
    |  <-- 7天内决策 -->
    |
阶段 2：正在用（投入了某个具体用途）
    |
    |-- 在学它的技术？        --> MINE/60-Learning/
    |-- 在做项目时用到了？    --> MINE/10-Work/ 或 20-Projects/
    |-- 写进了作品里？        --> MINE/50-Creative/
    `-- 处理个人事务需要？    --> MINE/40-Personal/
    |
    |  <-- 用完/项目结束 -->
    |
阶段 3：不活跃了（完成但偶尔要翻）
    MINE/70-Archive/[年份]/from-[来源]/
    |
    |  <-- 确定不再用 -->
    |
阶段 4：删除 / 或永久留在 Archive
``````

### 判断原则："现在时"而非"将来时"

问自己：**"我现在正在用它做什么？"** 而不是 **"它将来可能有什么用？"**

| 错误问法（将来时） | 正确问法（现在时） |
|---|---|
| "这个仓库将来可能用到工作里" | "我现在正在项目里用它吗？" |
| "这个文章将来可能需要查" | "我现在正在学这个主题吗？" |
| "这个数据将来可能有参考价值" | "我现在正在做需要它的事吗？" |

**如果"现在时"的答案都是"否"** → 它还停留在阶段 1（INBOX），或者直接归档。

> **为什么用"现在时"**：因为"将来可能有用"是囤积症的心理根源。大部分"将来可能有用"的文件，你永远不会再打开。用"现在时"判断，能帮你诚实地面对这个事实。真到将来有用时，去 Archive 里搜就行。

### 多重身份文件的处理

有些文件天然具有多重身份——一个算法仓库既是学习材料又是工作工具，一份财务模板既是个人事务又是工作产出。

**处理原则：物理位置跟随"主关系"，其他关系用快捷方式。**

``````
例：一个分割算法仓库，你既在学它，又在项目里用它

物理位置（跟随主关系——工作项目）：
    MINE/10-Work/分割分级项目/libs/awesome-seg/

逻辑入口（在另一个区放快捷方式）：
    MINE/60-Learning/awesome-seg.lnk  <-- 从"学习"角度也能找到

创建方式（Windows 符号链接）：
    mklink "MINE\60-Learning\awesome-seg.lnk" "MINE\10-Work\分割分级项目\libs\awesome-seg"
``````

**怎么判断"主关系"？** 看这个文件**最近一个月**主要在哪个场景下被使用。如果主要是工作项目在调用它，主关系就是工作；如果主要是你在读它的源码学习，主关系就是学习。

> **快捷方式不增加维护负担**：因为快捷方式是"只读引用"，文件实体只有一份。实体移动了，重建快捷方式即可（这种事很少发生）。

## 五、自我生长机制

### ① 编号留白——新区不打乱旧区

```
MINE/ 内部区号：10, 20, 30, 40, 50, 60, 70, 90（间隔 10，跳过 80）
                  ↑ 需要插入新区时：用 15, 25, 35, 45, 55, 65, 75

区内子号：01, 02, 03 ... 09（间隔 1）
           ↑ 需要更多时用 01a, 01b
```

> **80 故意留空**：作为预留扩展位，未来可能需要一个大类时使用。

### ② 什么时候新增分区

```
90-Misc/ 超过 20 个文件
    │
    ▼
检查这些文件的共性
    │
    ├── 它们属于同一个"关系类型"？
    │       → 新建一个编号区（如 80-XXX），把这批文件迁入
    │       → 更新本宪法
    │
    └── 没有共性？
            → 说明它们确实只是杂项，留在 90-Misc 没问题
```

### ③ 什么时候新增 SYSTEM 子目录

当你在根目录或 MINE 里发现一个新的"野生目录"（应用/环境自动生成的）时：

1. 在 `SYSTEM/` 下新建对应子目录
2. 移入文件
3. 修改应用配置指向新路径
4. 如果不方便改配置 → 用符号链接（`mklink /D`）

### ④ 宪法版本化

本文件（`_INDEX.md`）是宪法的载体。任何结构变更：
1. 修改对应章节
2. 在底部「变更记录」添加一条
3. 版本号 +0.1（小调整）或 +1.0（大改版）

**核心约束：任何变更都不能让已有文件的路径失效。新增可以，重命名/删除要极其谨慎。**

## 六、多盘符策略

你有多个盘符时，不需要每个盘都建完整体系。推荐策略：

| 盘符 | 角色 | 结构 |
|---|---|---|
| **C:** | 系统盘 | 不动，让 OS 和软件自己管 |
| **D:** | 主力数据盘 | 完整的 3+1 模型（MINE + SYSTEM + INBOX） |
| **E:** | 现有数据盘 | 逐步迁移到 3+1 模型（见迁移计划） |
| **G:** | 轻量知识盘 | 已有 Cognition 等目录，可保持现状或纳入 MINE |

**多盘符时的选择**：
- **方案 A（推荐）**：选一个盘作为"主力"，放完整的 MINE。其他盘只放 SYSTEM（环境/缓存）或 ARCHIVE（冷数据）。
- **方案 B**：按"关系类型"分盘——工作盘、个人盘、系统盘。但维护成本高，不推荐。

## 七、日常 SOP

### 每天

- 下载 → 自动进 `INBOX/_Downloads/`
- 截图/草稿 → 存 `INBOX/_Scratch/`
- 工作产出 → 直接存 `MINE/10-Work/[项目]/`

### 每周（10 分钟）

1. 清空 `INBOX/`——每个文件做决策：归入 MINE / 归档 / 删除
2. `_ToDecide/` 超 7 天的强制决策

### 每月（5 分钟）

- 检查 `MINE/10-Work/` 里完成的项目，移入 `70-Archive/`
- 检查根目录有没有新的"野生目录"，移入 `SYSTEM/`

### 每半年（30 分钟）

- 浏览 `70-Archive/`，确认无用的删除
- 回顾本宪法，是否需要调整
- 更新版本号

## 八、反模式诊断表

| 症状 | 诊断 | 修正 |
|---|---|---|
| INBOX 超过 50 个文件 | 一周没清理 | 立刻执行周清理 |
| 根目录出现非编号目录 | 又有应用/环境在根目录建文件夹了 | 移入 SYSTEM，改配置 |
| 桌面又有实体文件 | 没执行"唯一入口" | 移入 INBOX |
| `90-Misc/` 膨胀 | 可能需要新增分区 | 参考第四节 |
| 同一类文件散落多处 | 分区判断流程没执行 | 按判断流程重新归类 |
| `10-Work/` 超过 15 个项目 | 完成的没归档 | 不活跃项目移入 `70-Archive/` |
| 体系用了 3 个月还是乱 | 规则太复杂或不符习惯 | 简化规则，更新宪法 |

## 九、不可移动文件的处理规则

> **问题**：有些项目被工具"锚定"在某个路径上——Git 仓库、ZCode 会话、IDE 工程文件、Python 虚拟环境、CMake 缓存等，都绑定了绝对路径。移动这些项目会导致工具找不到文件、会话记录丢失、编译环境损坏。

### 识别"有锚定"的项目

一个项目如果满足以下**任意一条**，就视为"有锚定"，不能随意移动：

| 锚定类型 | 识别方法 | 移动后的后果 |
|---|---|---|
| Git 仓库 | 目录下有 `.git/` | remote 不受影响，但 IDE workspace 断 |
| ZCode 会话 | 在 `~/.zcode/v2/setting.json` 的 `lastWorkspaceSession` 里 | 旧会话找不到项目，对话记录"孤立" |
| IDE 工程文件 | 有 `.sln` / `.code-workspace` / `.vcxproj` | 工程引用路径全部失效 |
| Python 虚拟环境 | 有 `venv/` / `.conda/` | 环境内硬编码了绝对路径，需要重建 |
| CMake 缓存 | 有 `CMakeCache.txt` / `build/` | 编译缓存全部失效，需要重新 cmake |
| Docker 挂载 | `docker-compose.yml` 里有 volume 路径 | 容器挂载路径错 |
| 快捷方式 | 桌面/开始菜单有指向它的 `.lnk` | 快捷方式失效 |

### 三层处理策略

#### 策略 1：不动 + 映射表（推荐，零成本）

**物理位置完全不动。** 在 `_INDEX.md` 的「项目映射表」中记录逻辑归属。

适用场景：项目正在活跃使用，移动风险高。

#### 策略 2：新项目用新路径（推荐，零成本）

从采用本体系之日起：
- 新建的项目直接放在 `MINE/10-Work/` 或 `MINE/20-Projects/` 下
- 老项目保持原位，不强制迁移
- 当老项目不再活跃（超过 3 个月没用），才考虑迁移或归档

```
时间线：
  ──────────────┼──────────────
  过去           采用日          未来
  │              │              │
  老项目          今天            新项目
  保持原位置      开始用新体系     直接建在 MINE/ 下
  记入映射表
```

#### 策略 3：符号链接做逻辑搬家（中成本）

物理不动，在新位置创建一个目录符号链接指向旧位置：

```powershell
# 需要管理员权限的命令提示符
mklink /D "E:\MINE\10-Work\SuperAIPro" "E:\06GitProjects\SuperAIPro"
```

效果：
- ZCode/Git 打开旧路径 → 正常（物理路径没变）
- 文件管理器浏览 `MINE/10-Work/` → 也能看到 `SuperAIPro`（符号链接）
- 文件实体只有一份

适用场景：你希望在文件管理器里看到统一的新结构，但又不想破坏工具锚定。

**注意**：符号链接需要维护——如果旧路径删了，链接会断。定期检查映射表中的链接有效性。

### 项目映射表

> 记录"物理位置 → 逻辑归属"的对应关系。物理位置不变，但逻辑归属在此声明。
> 新项目如果直接建在 MINE/ 下，不需要记入此表。

| 物理路径 | 逻辑归属 | 锚定工具 | 状态 | 备注 |
|---|---|---|---|---|
| _(示例)_ `E:\06GitProjects\SuperAIPro` | `MINE/10-Work` | Git+ZCode+VS | 活跃 | 主力项目 |
| _(示例)_ `E:\08fun\trtsdk` | `MINE/20-Projects` | ZCode | 活跃 | |
| _(示例)_ `E:\02个人\MoneyMoneyMoney` | `MINE/20-Projects` | ZCode | 活跃 | |
| | | | | |
| | | | | |

> **维护规则**：
> - 新建项目如果直接放在 MINE/ 下，不用记入此表
> - 老项目迁入 MINE/ 后，从表中删除该行
> - 每半年检查一次：哪些老项目已经不活跃了？可以迁移或归档了？
